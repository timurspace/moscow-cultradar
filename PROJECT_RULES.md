# PROJECT RULES — «Культрадар»

> Стабильные правила проекта. Здесь нет текущих counts, статусов sweeps и списка «что делать сегодня» — это хранится в `PROJECT_STATE.md`.

## 1. Философия продукта

«Культрадар» — московская культурная афиша, которая должна заменять ручной просмотр множества афиш, но не решать за пользователя, куда ему идти.

Главное правило: **широкий подтверждённый календарь, а не короткий top**.

- Проходить площадки календарём, а не собирать случайные поисковые находки.
- Не удалять подтверждённое событие только потому, что оно не идеально совпадает со вкусом.
- Редакционный профиль использовать для приоритизации, а не как скрытый фильтр.
- Отсекать явный маркетинговый мусор, нерелевантный инфобизнес, дубли, отменённые и неподтверждённые даты.
- Кроссовер, праздничные гала и популярные программы допустимы в широком календаре с нейтральной редакционной маркировкой.

## 2. Редакционный статус и билетная срочность

Это две независимые оси.

`editorial_status`:

- `attention` — обратить внимание;
- `candidate` — серьёзный кандидат;
- `decide` — лучше решить заранее.

`ticket_urgency`:

- `none`;
- `no_rush`;
- `watch`;
- `buy`;
- `low`;
- `soldout`.

Сильное событие может иметь `no_rush`; среднее по редакционной ценности — `buy`, если места быстро уходят. Не выводить рекомендацию «покупать» только из ценности события.

`sales_status` — третий отдельный факт: событие может быть объявлено в сезоне/абонементе, но single tickets ещё не подтверждены.

## 3. Горизонты

`near` — ближайший горизонт решения. Для музыки обычно 2–3 недели; театр/опера могут попадать сюда раньше, если билетное решение нужно сейчас.

`buy` — купить/решить заранее: редкие программы, малые залы, премьеры, фестивали, сильные составы и события с риском ухода мест.

`far` — дальний радар. Обычно музыка 1–3 месяца, театр/опера 2–4 месяца, при необходимости до 6; сезонные анонсы могут лежать ещё дальше.

Горизонт — это момент принятия решения, а не право события существовать в базе. `events.json` может содержать более дальний опубликованный календарь.

## 4. Категории

Публичные категории:

- `music` — Музыка;
- `theatre` — Театр;
- `opera` — Опера / балет;
- `talks` — Лекции / разговоры.

## 5. Музыкальный профиль

Особенно отслеживать:

- академическую и камерную музыку;
- старинную музыку, барокко, historically informed performance;
- современную академическую музыку и XX–XXI век;
- редкий репертуар и необычные программы;
- сильных молодых исполнителей;
- независимые площадки;
- содержательные межжанровые проекты.

Не отбрасывать автоматически неизвестные имена, маленькие площадки, студенческие проекты, экспериментальные форматы и кроссовер. Для спорного события использовать editorial status/`why`, а не скрытое удаление.

## 6. Театр

Сначала проходить **весь опубликованный репертуар обязательной площадки**, чтобы не пропускать постановки. В публичный слой переносить широкий содержательный календарь, не сводя его к нескольким рекомендациям.

Приоритетные признаки:

- психологически сильная работа;
- серьёзная работа с классикой;
- современная драматургия;
- документальный и социальный театр;
- экспериментальная форма, если она служит материалу;
- сильная ансамблевая работа;
- редкие и масштабные спектакли.

Развлекательный/антрепризный хвост не копировать механически. Длинный спектакль допустим; длительность 4–6 часов указывать явно.

Приоритетные контуры: Маяковский, Театр Наций, Практика, Мастерская Брусникина, Театр.doc, Внутри, Место / Антон Фёдоров, Электротеатр Станиславский. Учебные площадки — отдельный discovery-контур.

Если у спектакля много дат, не плодить карточки без необходимости: хранить ближайшую дату и `occurrences`/список будущих показов, когда схема это поддерживает.

## 7. Опера / балет

Это отдельный полноценный раздел. Обязательно мониторить:

- Большой театр;
- МАМТ;
- Новую Оперу;
- Геликон-оперу;
- Центр оперного пения Галины Вишневской;
- концертную оперу Зарядья, Филармонии и Консерватории;
- фестивальные/независимые проекты.

Балет мониторить вместе с оперным контуром. Проходить опубликованный репертуар широко; editorial status и `why` отвечают за приоритет, а не скрытое удаление стандартного репертуара.

Для оперы по возможности хранить композитора/название, постановщика, дирижёра, ключевых солистов, тип постановки, длительность, цену и `why`. Для премьеры до отзывов обычно использовать осторожную редакционную маркировку.

## 8. Talks

Искать содержательные разговоры по литературе, философии, истории, психологии, музыке, искусству и культурной истории. Отсекать generic self-help, мотивационные шоу, инфобизнес и поверхностный edutainment.

Обязательные discovery-контуры: Good Talks Club, Лекторий «Достоевский», `Прямая речь`, музейные и независимые площадки.

Организатор talks не становится площадкой автоматически: публиковать событие под фактическим venue.

## 10. Discovery и primary source

Порядок работы:

1. Первый weekly discovery-проход — свежие публикации и сезонные анонсы ClassicalMusicNews.
2. Затем — официальные календари площадок по `sources.json` до текущего audit horizon.
3. Дополнительные discovery: Русконцерт, Good Talks Club, Telegram/VK/новости ансамблей и театров, новые пространства.
4. Каждый discovery-кандидат перепроверять по официальной странице площадки/организатора.
5. Сверять с `events.json` по id, названию, дате и venue; не дублировать.

`source_url` по возможности ведёт на **первичную официальную страницу конкретного события**.

Если отдельной event-page нет, допустим официальный календарь/страница площадки. Агрегатор хранить как `discovery_url`/`discovery_source`, но не как основной `source_url`, если найден официальный источник.

## 11. Venue / organizer / discovery separation

`sources.json` schema v2:

- `venues` — реальные физические площадки;
- `discovery_sources` — источники обнаружения;
- `monitor_entities` — ансамбли/организации/персоны, за которыми следим независимо от venue;
- `monitor_groups` — родительские группы нескольких физических площадок.

Для события с физической площадкой:

- `events[].venue` должен буквально совпадать с `sources.venues[].name`;
- `source_label` должен быть названием фактической площадки, а не СМИ/ансамбля/организатора;
- организатор хранится отдельно в `organizer`;
- discovery — отдельно в `discovery_source` / `discovery_url`.

Нулевой `coverage_YYYY.month` **не доказывает**, что афиша месяца проверена и событий нет. Если месяц ещё не опубликован — зафиксировать это в `coverage_note`; если опубликован — провести sweep.

## 12. Схема карточки

Базовые поля события:

`id`, `category`, `horizon`, `featured`, `start`/`end` или `date_only`, `title`, `display_title`, `tags`, `visible_tags`, `venue`, `place`, `location`, `people`, `price`, `why`, `editorial_status`, `ticket_urgency`, `details`, `source_label`, `source_url`, `verified`.

Для `music` / `opera` card schema v2 использовать по возможности:

- `composers: []`;
- `works: []`;
- `venue_short`;
- `program_status`;
- `season`;
- `sales_status`;
- `card_schema_version: 2`.

Если точная программа не опубликована, не восстанавливать её по памяти: честно заполнять `program_status`.

Время никогда не угадывать. Если официально известна только дата — использовать `date_only: YYYY-MM-DD`.

При переносе события по возможности сохранять стабильный `id`, чтобы не ломать приватный статус пользователя.

Отменённые события не держать как активные карточки; перенос хранить по новой актуальной дате.

## 13. Фестивали и циклы

Фестиваль/цикл не заменяет отдельные карточки событий. Каждая дата должна оставаться самостоятельным календарным событием. В будущем допустимы `festival_id`, `cycle_id`, `series_id` и фильтры-кластеры, но не вводить их раньше реальной потребности.

## 14. Приватный слой

Публичный GitHub не должен содержать:

- личные статусы и заметки;
- номера заказов;
- QR билетов;
- токенизированные ссылки;
- email приглашённых;
- приватные календарные данные.

Текущий localStorage key: `afisha-private-v2` — сохранять для совместимости.

Личные состояния: `want`, `bought`, `later`, `skip`, `visited`; `timofey` — отдельный orthogonal boolean. Дополнительные поля: `noteBefore`, `noteAfter`, `calendar`, visited snapshot.

При `visited` хранить приватный snapshot события, чтобы публичную прошедшую карточку можно было позже удалить без потери личной истории.

## 15. Календарь

Сайт нужен для поиска и решения; календарь — для обязательства и истории.

Поддерживаются `.ics` и prefilled Google Calendar URL. OAuth, чтение внешнего календаря и фоновая синхронизация не нужны без отдельной задачи.

Не подставлять приватные заметки в публичные/Google Calendar URL автоматически.

## 16. Export / import

Ручной export/import — переносимость приватных данных между устройствами. LocalStorage не зашифрован; в нём допустимы культурные заметки, но не секреты, токены, QR и платёжные данные.

При изменении приватной структуры повышать `schema_version` экспорта и сохранять обратную совместимость настолько, насколько это разумно.

## 17. QA данных

Перед публикацией:

- JSON должен парситься;
- id уникальны;
- обязательные поля присутствуют;
- дата/время не выдуманы;
- для Moscow datetime использовать корректный offset `+03:00`;
- `end` не раньше `start`;
- category/horizon/editorial/ticket enums согласованы с интерфейсом;
- venue присутствует в `sources.venues`, кроме специальных служебных случаев вроде `Watchlist`;
- primary `source_url` официальный, если возможно;
- `source_label` согласован с физической площадкой;
- discovery/organizer не смешаны с venue;
- переносы, sold out и отмены проверены;
- coverage не трактуется по одному только числу 0.

Warnings validator — повод для ревью, а не автоматическое доказательство дефекта. Fatal должны быть ошибки, которые однозначно делают данные некорректными.


### Работа с большим `events.json` через GitHub connector

`events.json` уже достаточно большой, поэтому обычное чтение файла через GitHub file-content endpoint / `fetch_file` может вернуть пустое или усечённое содержимое. Ошибка `JSON.parse` после такого чтения **не означает автоматически, что файл повреждён**.

Для полного чтения `events.json`:

1. Получить актуальный SHA файла из GitHub.
2. Прочитать содержимое через Git blob по SHA, а не полагаться на обычный file-content response.
3. Выполнять массовый анализ или изменение только после успешного полного `JSON.parse`.
4. Перед записью проверить ожидаемое количество событий и ключевые инварианты, относящиеся к задаче.
5. После commit проверить соответствующий GitHub data-audit; если менялись публикуемые файлы — также Pages deployment.

**Нельзя перезаписывать `events.json`, если полученная копия была усечена, пуста или не прошла полный `JSON.parse`.**

## 18. GitHub workflow

Рабочий цикл:

1. Прочитать `PROJECT_HANDOFF.md`, `PROJECT_STATE.md`, `PROJECT_RULES.md`.
2. Проверить фактический `main` и Actions; GitHub выше документации по приоритету.
3. Собрать/проверить события и источники.
4. Менять только нужные файлы; не трогать UI при content-only задаче.
5. Прогнать data QA / validator.
6. Делать атомарный commit.
7. Дождаться Pages build и data audit, если он был триггернут.
8. Обновить `PROJECT_STATE.md`, если изменились counts, coverage, automation, schema или ближайшие задачи.

GitHub Pages публикуется из `main`/root.

## 19. Что не начинать заново

Не создавать новый repo/brand, не переносить проект на другой GitHub user и не объяснять заново базовую настройку Pages. Принято:

- user: `timurspace`;
- repo: `moscow-cultradar`;
- brand: «Культрадар»;
- public site: GitHub Pages.

Если правило из этого файла противоречит фактической схеме/коду, сначала проверить, что изменилось. Фактический GitHub имеет приоритет; затем синхронизировать документацию.
